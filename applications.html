Application MCP

Work with an application's current document

An assistant can read an application's open document or workflow, suggest a change, and invoke an action the application declares. The application keeps its state, interface and commit points. OpenAbstractions' application profile gives those interactions shared meanings across integrations.

Through application MCP, agents can discover which actions an app supports, see their inputs and open supported actions. On a ComfyUI workflow opened through OpenAbstractions, an agent asks before it edits the canvas, and the person chooses Allow once, Always allow or Not now. Check released-package guidance and recorded interaction evidence for available behavior.

Assistant → OA → application

  1. Discover and read. The assistant learns the application's declared commands and open contexts. A context identifies one document or workflow in a particular application instance and epoch.
  2. Check and route. For OA-mediated calls, the runtime checks the caller's identity, current permission and selected application. A description or native label supplies information; enforcement needs actual identity and lifecycle evidence.
  3. Commit and report. The application validates the request, owns its domain rules, and reports the result. The assistant reads the resulting state or follows accepted work.

An entity is an application-defined item, such as a node in a workflow. Its kind describes properties and their roles. The projection includes entities and collections; snapshots also carry selections. Selection and ephemeral fields stay outside the revisioned projection, and secret fields stay outside published state and changes. An integration chooses this projection rather than exposing every internal object.

A suggestion stays tied to what was read

Imagine an assistant reads a workflow at revision R and proposes changing a node parameter. The person then edits the workflow. If the assistant applies its proposal with the old expected revision R, the call returns conflict and changes nothing. It can read the new state and prepare another suggestion. The person's direct in-app Apply follows the application's own rules. Reopening or replacing the context changes its epoch, making old references stale.

Revisions are opaque tokens. Changes let a client follow the application's commit points; a lost position requires a fresh snapshot. A proposal records a suggestion without changing the document. Apply performs the declared action. For an undoable edit, one undo group covers the steps owned by that call, subject to the contract's later-edit checks.

Long-running work can answer accepted with a job handle. The client follows that job for its outcome. Losing a reply after sending a command leaves an unknown outcome: inspect state, the job or the recorded idempotency result before deciding what to do. The bridge never automatically resends a sent call.

Command classes describe effects such as read, edit, spend or send. Classification helps OA select the right permission check. A class or MCP annotation grants no permission. The application still owns its business rules and daily limits.

MCP tools and resources already support application integrations. OA composes them with its application profile and native policy boundary. MCP Apps addresses a related presentation layer: servers provide UI resources for a host to render, with negotiated UI communication. This page describes operating application-owned state and actions; an MCP Apps interface can be considered separately.

The current ComfyUI source demonstrator

The reviewed implementation exposes a bounded view of built-in KSampler nodes and their steps values. An assistant can read that context, reveal one node, display a proposed before-and-after value in ComfyUI, and request a separately authorized node.set_widget edit. The edit accepts only an integer from 1 to 10,000 for steps. The shared application core owns proposals and revisions; the app-owned interface shows the suggestion and preserves the person's selection and focus.

The runtime checks the kept signed application declaration, actual host ownership and current permission, and records mediated calls. The ComfyUI adapter checks the current workflow, node, widget and before value immediately before writing; an enabled or unverified auto-queue mode refuses the edit. These are source-level controls. A real installed browser/backend demonstration remains unproven. Queueing, templates, arbitrary widgets and full-editor control are outside this demonstrator.

The three application-model tools (oa_applications_describe, oa_applications_commands_list and oa_applications_command_call) use abstraction.facade/applications@3. The runtime decides each call from the kept manifest, the command's class and the caller's rights. A refusal keeps its own outcome and reason, and the tool result carries isError.

Setup tools

oa_setup_fit takes one use (chat, code, vision, embed, image or video) and returns the catalogue's entries in rank order. Each entry carries a title, a family, a fit word (fits or no; slow is reserved for later), whether a runtime already serves it, its download and need in bytes, and which entry is this computer's pick. The call needs the router's inventory.read right and downloads, selects and hosts nothing.

oa_setup_prepare takes code, image or video and asks OpenAbstractions' setup step for that use. The reply is asked, already_set_up or cannot_run with a reason; invalid, forbidden and unavailable report a refused or unreachable request. The person answers OA's own setup question, which names the application, and the reply never carries that answer. After the person answers Not now, OA asks for no application for 24 hours or until the person starts Setup from Settings. The application restarts after the person sets the use up.

Messages between agents

A separate, dedicated native composition adds messaging tools for Claude, Codex and OpenCode once its kept application instance has opened an inbox. oa_messages_inbox_open takes an optional context and uses the connection's own context when it is omitted. oa_messages_prepare names a receiver and returns send_arguments for oa_messages_send; without a live inbox it answers receiver_withdrawn (the receiver's connection closed), receiver_lapsed (the connection stopped renewing) or receiver_unavailable (no authorized live inbox is visible). Only the person can allow a direction through oa_messages_request_access. Source tests establish these behaviors; installed receiving and idle wake keep their own acceptance.

Developer details

The standalone binding uses standard MCP newline stdio. OA's signed native host recipe uses an explicit private length-framed carrier with the same shared MCP session semantics. It is a custom MCP transport, with no autodetection or fallback to ordinary stdio. The MCP transport specification describes standard and custom transports.

Generated application records preserve opaque JSON bytes. Canonical record text is authoritative in the tool's text content; structured content supplies the corresponding JSON view. This keeps raw numeric values and record validation intact across bindings. The SDK handles that detail while the application declares its state and actions.
