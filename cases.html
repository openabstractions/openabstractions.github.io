What applications gain from the service boundary

Each case starts with a task a person recognizes and one capability that can span an operating-system facility, a local program, or a remote service. OA checks permission and preserves the capability's meaning across those implementations.

Find an application integration · See how AI applications share models and memory. Measurements below describe dated development experiments. The release notes record current qualification.

Development preview: the OpenCode refresh and saved preference and Comfy workflow examples below retain their separately recorded verification and limits. The latest runtime release notes identify shipped packages.

An image editor and OA's own engines take turns on the graphics card

The task

ComfyUI needs more of the graphics card than is free. OA's model server holds a model on the same card, and a stock chat engine such as LM Studio may hold another.

OA's role

Integrated programs hold a lease for the memory they use: OA's own engines, and ComfyUI with OA's integration. When ComfyUI asks for room, the resource service asks those lease holders to yield and grants the lease once its own measurement shows the memory free. A stock engine holds memory under no lease. OA measures it as memory it does not manage and names that program to the person.

The ComfyUI connector takes the card lease for the models ComfyUI loads. OA's model server stops an idle engine when asked and answers once the measurement confirms the memory fell. The resource repository is preparing its first tagged release.

Earlier design, 2026-09-22: OA drove stock LM Studio's unload endpoint, and LM Studio yielded 21,446,795,264 bytes in 7.305 s; a deny rule refused the same ask in 146 ms. research/resources/COMFY-CARD-2026-09-22.md, sections 1 and 3. OA now measures and names stock engines and drives only integrated ones.

A coding assistant reaches every local model through one runtime

The task

An OpenCode user with a local model wants to chat with it through OA, with nothing to type into OpenCode's own configuration.

OA's role

The adapter's configure.js reads the router's servable chat families through the runtime and writes OpenCode's provider block for them.

Observed UI demonstration: the patched OpenCode 1.18.31 TUI refreshed its model chooser in the same running process after Ctrl+Alt+R. A newly advertised local model appeared from a deterministic fixture; the check sent no prompt.

Keep one model preference when a local engine goes offline

The task

A coding session should keep using its chosen model family when one local engine is unavailable.

OA's role

A saved, ordered selection policy names eligible local candidates. Each new request selects an available candidate and records the model that answered.

Observed API demonstration: two completed turns in one OpenCode session used the same saved preference. Lemonade answered the first; after it became unavailable, Ollama answered the next fresh request. OA identified the actual host and model for each answer. The preference alias has not yet been shown in OpenCode's rendered model picker, and first-use policy setup was not observed.

Controlled local-provider run; no hosted account, model download, or paid request.

A model file downloaded once is served by another engine

The task

A model file (GGUF) sits in the Jan app's model folder (the jan store) on this machine. LM Studio never downloaded it and cannot see it.

OA's role

The model bridge resolves the file through the storage inventory and lends it into LM Studio's own models folder by link, once the operator permits lending to that engine.

On 2026-09-22 a 46 MB GGUF from the jan store was hard-linked into LM Studio's models folder in 6.3 seconds end to end: the first lend attempt was refused not_permitted, the lend after the rule placed one hard link, and LM Studio listed the file under its own derived name inside a 30-second window. unlend removed the link and its directories again; the source file in the jan store never moved.

Measured: 45,949,216 bytes in 6.3 s end to end. abstraction-provider-modelbridge/README.md, "Measured".

Model bridge source and recovery guide. Its first tagged release is in preparation.

A coding assistant can change model providers

The task

A coding assistant streams an answer from a requested model. The operator may run that model locally today and through a remote host tomorrow.

OA's role

The assistant requests a model and execution placement. OA checks its rights, selects an eligible declared host, and mediates a connection pinned to that provider declaration.

The same inference family also carries embeddings, speech synthesis, transcription, live sessions, and image generation. Each modality has a defined request and a streamed or final result. Language support lists the languages that call inference; each provider declares the modalities it serves.

An image editor can return to the same download

The task

A node-based image editor needs a multi-gigabyte model. The user closes the editor while the transfer is active and later returns.

OA's role

The editor submits one retained job. OA owns progress and settlement. The editor saves the returned operation reference and observes the same accepted work after restart.

The ComfyUI source adopter supplies this integration path. Storage lookup can reuse matching content before the editor requests another transfer.

Verify workflow assets, approve the canvas change, and render in ComfyUI

The task

Prepare a pinned FLUX.2 Klein workflow with its diffusion model, text encoder, and VAE, then produce an image in ComfyUI.

OA's role

The adopter checks the required files, verifies their declared digests, and asks before replacing the current canvas. ComfyUI remains in control of the final Run action and image generation.

Observed ComfyUI demonstration: all three verified assets were already present. The run checked readiness, received approval for one canvas replacement, then invoked ComfyUI Run. The editable 512 × 512 workflow completed a four-step CPU render. This confirms prepared workflow use; first-time asset acquisition through the UI remains untested.

This was a repeat-use demonstration with all required files present. The first-time UI download path and matched setup savings remain unmeasured.

A Comfy render waits for OA's Lemonade build to finish its chat request

The task

A Comfy workflow needs the graphics card while OA's Lemonade build is serving a local chat request.

OA's role

OA's Lemonade build holds a card lease for its engines. When ComfyUI with OA's integration asks for room, the resource service asks that holder to yield. The holder stops its engine once no request uses it, and the service grants ComfyUI its lease after its own measurement confirms the memory fell. A stock Lemonade holds memory under no lease. OA measures it as memory it does not manage and names the program to the person.

A chat request still running keeps its engine until it returns (resource CONTRACT.md RES-L3), and ComfyUI's request waits for it.

Earlier design: a demonstration asked a stock Lemonade to unload its model once Qwen became idle, and the Comfy workflow then rendered. That scenario's final process-measurement check failed and was never rerun. OA now measures and names stock engines and drives only integrated ones (resource CONTRACT.md RES-L3).

An assistant can open an app and propose a specific action

The task

An assistant needs an image editor, then wants to preview a sampling-step change in the document the user is viewing.

OA's role

With permission, OA activates an operator-registered app and waits for that app to report readiness from the same signed-in session. The app reports its current document and revision.

The OA Model Context Protocol (MCP) gateway lists visible applications under its own verified program identity. Activation uses the facade API. A separate image-editor adapter owns the preview, apply, and readback tools. A proposal carries the exact app instance, document, and revision; a changed document produces a stale result. Presentation stays inside the requesting task and application tool surface.

This is a scoped development composition with current live evidence. OA defines no universal application UI protocol. Language support records the tested source and limits.

An operator can see and control the boundary

Rights and providers

The OA Panel shows which programs may do what, which providers and model hosts are registered, whether they are ready, and which saved credential names exist. Revoking permission changes later decisions.

Configuration and evidence

The Panel edits revisioned user settings, follows effective configuration, reads retained logs, and shows caller identity and provider diagnostics.

Limits remain part of the product

  • Provider registration, application visibility, activation, invocation, and effect authority are separate grants.
  • A lost submission reply produces an uncertain state and reconciliation with the original owner.
  • Local and remote execution placement remains explicit through provider selection and forwarding.
  • Current feature evidence uses controlled integrations and actual local applications. Release packaging and broader provider interoperability require their own evidence.
