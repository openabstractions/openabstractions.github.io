A useful result names the source revision, environment, caller, provider, action, and observable outcome. Coverage turns those records into current capability verdicts.

How to judge a result

ScopeThe exact operating system, architecture, language, application, process boundary, and provider.
BehaviorThe request and observable result, including refusals, interruption, replacement, and restart where relevant.
AuthorityThe component that supplied caller identity, rights, provider selection, credentials, and outcome evidence.
LimitsThe boundary of the run. Skipped, hidden, unavailable, and unexercised checks remain unverified.

Claims that require separate evidence

  • Source compilation, installer behavior, startup lifecycle, upgrade safety, and published packages each need their own run.
  • A controlled provider proves the mediated boundary for that provider and environment.
  • A live application proof covers the named application, workflow, host, and permissions exercised in that run.
  • Transport authentication supplies peer evidence; the service still checks the action against the verified program and account.
  • A cancelled wait proves the wait ended. Operation cancellation needs a later observed outcome.
  • Human comprehension requires a separate user-facing check; technical effect evidence covers system behavior.
