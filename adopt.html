Adopt a service capability

An application resolves a service and calls its language-native client. The service owns its data and work. Begin with logging; add durable jobs when the application needs recoverable acceptance.

Development source guidance. The examples below match the current source API. Verify that your chosen public revision contains it and that its dependencies resolve. Historical release tags and coverage records do not establish availability of a newer API.

Go: resolve and log

Use Go 1.26 or newer and the facade package. Its README gives module selection and a complete example:

package main

import (
    "context"
    "log"
    "time"

    facade "github.com/openabstractions/abstraction-facade/go"
)

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()
    events, err := facade.Discover().ResolveLog(ctx, facade.Requirements{})
    if err != nil {
        log.Fatal(err)
    }
    if err := events.LogContext(ctx, 0, "worker started", map[string]string{"component": "worker"}); err != nil {
        log.Fatal(err)
    }
}

The context bounds resolution and the write. A later call can use a fresh context with the same binding. Failure to resolve returns an error and leaves installation with the operator. Logging frame delivery supplies no durable logging acknowledgement.

C++: consume installed packages

C++17 uses find_package(abstraction_facade CONFIG REQUIRED) and abstraction::facade_client. The source installation instructions name the six public source dependencies, install prefix and outside consumer commands. Discover().ResolveLog() performs resolution and can throw before sending a log event.

The complete C++ logging example includes an exact six-repository public revision lock and clean-source build commands. That tested path requires no operator-selected revision set.

Go, C++ and Python have typed service clients in the current source. See the Python package instructions for dependencies and supported capabilities. Rust and JavaScript connectors require explicit server-trust configuration. Check published package versions separately.

Make the service available

The operator installs and activates a compatible shared runtime. See runtime distribution for package and platform instructions. A built package is evidence for its build scope; check the installed lifecycle evidence for your platform.

For development, a compatible openabstractions serve runtime runs in the foreground. Its default services include logging, configuration and durable jobs. Routing needs a configured provider. openabstractions status --json reports capability readiness separately from installation or supervision evidence. An unavailable optional capability can coexist with a healthy host.

ABSTRACTION_RUNTIME_ENDPOINT selects an explicit bootstrap for an isolated runtime. Applications receive selected service references and keep shared storage behind those APIs. The current facade binds local transport; remote transport support remains unfinished.

Durable work and existing engines

Use typed job acceptance, observation and result access for service-owned work. Retain the request key, history epoch, logical owner and required guarantees before submission. A lost reply remains uncertain: reconcile the same identity with its original owner. A cancelled wait ends the wait; CancelWork requests cancellation of the work.

An explicit legacy adapter can keep an existing engine during migration. Its lifetime and storage requirements belong to that integration. Direct FileStore and Runner examples describe provider implementation; they are separate from the primary facade's application boundary.

Check your integration

Implementations can run the public conformance suite through its documented driver protocol. Read its scope and prerequisites before running it.

Compile outside the source workspace, then exercise success and an absent runtime using isolated endpoints. Preserve the explicit failure and verify that the application created no provider storage. The installed C++ binding workflow records source revisions and platform results. Coverage records wider conformance scopes; inspect dates and revisions before using a result.

Agents preparing an adoption or patch should use the contribution checklist. It asks for dependency, runtime, guarantee and failure evidence.

Report a mismatch

File a focused issue or patch in the capability repository with the selected revision, input, expected contract behavior and actual result. Security reports follow SECURITY.md.
